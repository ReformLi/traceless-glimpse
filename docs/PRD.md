## 1. 项目概述

### 1.1 背景

现有网页视频下载工具在便利性上成熟，但存在两个结构性局限：其一，用户使用的是他人打包的二进制应用，"不收集数据"依赖开发者声明而非可验证架构；其二，功能与交互固定，无法按个人工作流深度定制。

### 1.2 产品定位

**无痕掠影**是一个以 AI Agent 为编排核心、以本地执行为默认、以浏览器隔离嗅探为入口的视频获取工具。它在数据路径上不设第三方中间节点，在浏览器身份上不污染用户日常环境，在工作流上允许用户用自然语言与配置深度定制。

### 1.3 一句话描述

> 在隔离的浏览器里嗅探，在本地完成下载与处理，数据没有可去的地方。

### 1.4 设计原则

1. **架构即隐私**：不依赖"承诺不收集"，而依赖"数据无处可去"。
2. **默认拒绝**：网络边界、文件写入、凭据读取默认关闭，显式放行。
3. **身份隔离**：Agent 的浏览器行为与用户日常身份物理分离。
4. **可审计**：每一个外部请求、每一次凭据读取、每一个落盘文件都有可查记录。
5. **个性化优先于通用性**：宁可少一个内置功能，也要保证用户能改。

## 2. 目标与非目标

### 2.1 目标

- 支持从主流视频网站及通用网页嗅探并下载媒体流。
- 浏览器嗅探过程使用独立上下文，任务结束即销毁。
- 所有解析、下载、合并、转码在本地完成，不上传任何媒体内容。
- 提供 Agent 自然语言编排能力，支持用户自定义下载策略。
- 提供可审计的安全边界：SSRF 防护、凭据最小接触、输出沙箱、日志脱敏。

### 2.2 非目标（v1 明确不做）

- 不破解 DRM（Widevine / FairPlay / PlayReady），检测到加密流仅报告不支持。
- 不提供云端转码、云端转录、云端账号体系。
- 不做内容分发、分享、二次上传功能。
- 不内置广告、分析 SDK、遥测上报。

## 3. 目标用户与核心场景

| 用户类型   | 核心诉求                    | 典型场景                  |
| ------ | ----------------------- | --------------------- |
| 隐私敏感用户 | 不想让下载行为与日常浏览身份关联        | 用独立上下文嗅探，任务结束无残留      |
| 内容研究者  | 需要批量、规范化地归档公开视频         | 自定义命名规则 + 本地转录 + 字幕提取 |

| 普通用户   | 粘贴链接即可下载，但担心数据安全        | 一键下载 + 明确的安全提示        |

## 4. 术语

| 术语                      | 含义                                        |
| ----------------------- | ----------------------------------------- |
| 嗅探（Sniff）               | 通过监听浏览器网络请求发现媒体流地址                        |
| 隔离上下文（Isolated Context） | 独立 Cookie jar、存储、缓存、Service Worker 的浏览器会话 |
| 本地引擎（Local Engine）      | 运行在用户设备或用户自托管机器上的解析与下载服务                  |
| 惰性 Cookie               | 默认不发送 Cookie，仅在请求被拒时按最小范围重试一次             |
| 输出沙箱                    | 权限受限、路径白名单校验的专用写入目录                       |

## 5. 产品形态与部署架构

### 5.1 三种形态（同一 Agent 核心，不同外壳）

1. **桌面本地引擎**（主力）：本地 HTTP 服务，承载 Playwright 嗅探、yt-dlp 下载、FFmpeg 处理。
   M15 起增加 `desktop/` 控制面板与单文件 exe 作为外壳（默认监听 `0.0.0.0:8730` 以便手机接入），
   M16 起内置下载控制台，电脑端可独立完成全流程；引擎无入站鉴权，仅限可信局域网。
2. **Android App**：`com.hpu.browseguard`，作为客户端与轻量入口，可连接本机引擎（USB / 可信局域网明文 HTTP，**TLS 本期未实现**）或使用内置轻量下载能力。
3. **CLI / MCP Server**：`bgv` 命令与 MCP 工具，供技术用户与 AI 客户端调用。

### 6.2 下载引擎（FR-DL）

| 编号       | 需求                                              | 优先级 |
| -------- | ----------------------------------------------- | --- |
| FR-DL-01 | 封装 yt-dlp 作为核心解析器，支持其覆盖的站点；支持直接传入嗅探得到的媒体地址      | P0  |
| FR-DL-02 | 展示可用格式列表（容器、分辨率、码率、编码、是否含音轨），支持精确选择与"不超过指定画质"策略。**安全设计取舍**：formatId 不支持透传——不接受 yt-dlp 原始 `-f` 字符串，只走结构化 selector（PROTOCOL §6.3） | P0  |
| FR-DL-03 | 分离音视频轨自动调用 FFmpeg 合并；支持容器转换与重封装                 | P0  |
| FR-DL-04 | 支持断点续传、并发任务队列、失败重试（可配置次数与退避）                    | P0  |
| FR-DL-05 | 支持字幕下载与提取（含自动生成字幕，若源站提供）                        | P1  |
| FR-DL-06 | 支持本地转录（Whisper 本地运行），音频不出设备                     | P1  |
| FR-DL-07 | 单文件大小、总时长、并发数均设默认上限，可显式调高                       | P0  |
| FR-DL-08 | 下载完成后进行完整性校验（文件可解析、时长非零），失败标记为不完整               | P1  |
| FR-DL-09 | HLS 分段并发数可配置，默认 3、范围 1~8；引擎端与 Android 端字段名、默认值、范围、越界策略一致 | P0  |

**FR-DL-09 实现口径（M25）**：字段名 `hlsConcurrency`，默认 **3**，闭区间 **1~8**，越界**直接拒绝**而不是夹取（夹取等于静默改用户意图）。四个入口分别处理：API 返回 422 并给固定文案；Android 设置页拒绝保存、保持原值、记审计，设置项以 1~8 离散滑杆呈现（8 个整数档位、7 段分隔断点、默认 3，第一层约束由档位提供）（双层）；环境变量 `BGV_HLS_CONCURRENCY` 越界记审计并回落 3、不阻断启动；旧配置缺失或存储损坏回落 3。优先级固定为 `请求字段 > 环境变量 > 默认 3`（PROTOCOL §3.8）。

**直链强制单连接顺序下载**：非 HLS、非分片的直链路径禁止多线程 Range 并发；`Range` 只用于断点续传。HLS 分片路径才走上面的并发配置。分离音视频轨时**每条流各 N**（默认 3+3），不把 N 平摊。该字段只活在单次下载的运行态里，**不入库**；引擎重启后正在下载的任务按默认 3 续跑。

**边界说明**：并发数仅使行为落在正常播放器区间，不改变通信可见性。目标地址、请求头、连接数上限与明文 HTTP 的事实一概不变——本项不提供、也不宣称任何「防检测 / 防追踪」能力，不新增相关文案，也不引入限速开关。

| 编号        | 需求                                                       | 优先级 |

| FR-SEC-02 | Cookie 采用惰性模式：默认不发送；被拒时仅对当次请求、仅默认浏览器、仅一次重试；使用副本，不写回原文件   | P0  |
| FR-SEC-03 | 输出目录独立、权限 `0700`；拒绝写入 `/`、`$HOME`、当前目录、`PATH` 内目录；扩展名白名单 | P0  |

| FR-SEC-08 | 检测到 DRM 加密流时明确报告"不支持"，不尝试绕过                              | P0  |
| FR-SEC-09 | 提供"隐私自检"页面：展示当前监听地址、出口代理、Cookie 策略、输出目录、缓存占用、最近一次清理时间    | P1  |
| FR-SEC-10 | 依赖清单与版本可查，提供安全更新提示（yt-dlp / FFmpeg / Playwright）         | P1  |

### 6.9 本机执行者（FR-LOC，v0.3 新增；M4–M9 已实现）

路径 B 在实现中越过了「只负责发现、把活交给引擎」的定位：Android 端现在自己就能完成发现→下载→封装。
这是产品级变化，必须写在需求里而不是只写在代码注释里，否则「数据不出设备」的承诺无法被核对。

| 编号       | 需求                                                                        | 优先级 | 状态 |
| -------- | ------------------------------------------------------------------------- | --- | -- |
| FR-LOC-01 | 设置页在「引擎」与「本机」两个下载执行者之间切换；切到本机后本地代码路径不构造引擎请求体，失败归因用本地码，不借用协议码         | P0  | 已实现 |

## 9. 验收标准（关键场景）

1. **隔离性**：执行两次嗅探任务后，第二次任务不携带第一次任务的任何 Cookie；`context.close()` 后检查存储目录无残留。
2. **凭据最小化**：普通可下载页面全程不读取任何 Cookie 文件；被拒场景下仅发生一次读取、一次重试，且原 Cookie 文件 mtime 不变。
3. **SSRF**：提交 `http://127.0.0.1`、`http://169.254.169.254`、`http://10.0.0.1` 均被拒绝；构造指向私有地址的 302 重定向同样被拒绝。
4. **写入沙箱**：将输出目录设为 `$HOME` 或 `/` 时被拒绝并给出提示；非白名单扩展名不落盘。
5. **日志脱敏**：导出日志中检索不到 Cookie 值、token、完整敏感查询参数。
6. **DRM**：对加密流返回明确的"不支持 DRM"错误码，不产生下载尝试。
7. **个性化**：M24 的「视频标题命名（可空）」在真实任务中生效，后缀由系统按真实容器补；纯音频下载与合并音视频两条后处理链按模式可用性生效。**命名模板变量已随封板裁决砍掉，不再属于验收项**（见 FR-PER-01）。
8. **一键清除**：执行后隔离上下文、缓存、临时文件、日志清零，媒体文件保留。
9. **HLS 并发（M25）**：默认 3；`1` / `8` 生效，`0` / `9` / `-1` / 非数字被拒绝；引擎与 Android 取值一致；缺配置回落 3；直链仍是一条 GET 顺序拉完、无并发 Range。

### 12.3 协议模型共享方案（KMP ↔ Pydantic）

采用 **JSON Schema 作为中间契约**，而非 Protobuf 或 OpenAPI 生成器。理由：你的协议是手写 JSON 文档，JSON Schema 的声明式约束（`required`、`enum`、`minimum`）与协议第 3 节的结构直接对应；Kotlin 侧通过 `kotlinx.serialization` 的 `@Serializable` + `@SerialName` 映射字段，Python 侧通过 Pydantic 模型实现同一 Schema。

具体落地：

1. **`shared/commonMain`** 定义 Kotlin `data class`，例如：
   
   ```kotlin
   @Serializable
   data class Task(
       val id: String,
       val sourceUrl: String,
       @SerialName("cookiePolicy") val cookiePolicy: CookiePolicy,
       // ...
   )
   @Serializable
   enum class CookiePolicy { NONE, LAZY, EXPLICIT }
   ```

2. **`engine/models.py`** 定义 Pydantic 模型，字段名与 JSON Schema 对齐；`cookiePolicy` 使用 `Literal["none","lazy","explicit"]`。

3. **Schema 对账**：KMP 模块导出 `schema/*.json`，Python 侧 Pydantic 的 `model_json_schema()` 同样导出，`scripts/check_schema.py` 比较两份 Schema 的 `required` / `properties` / `enum` / `type` / `x-nullable` 五类，不一致则非零退出。项目为本机单人开发，未接托管 CI，这道对账在提交前与发版前手动跑。

4. **协议安全约束的编译期固化**：`Task` 的 Kotlin 数据类中**不存在** `cookieFile`、`browser`、`headers` 字段；任何试图传入这些字段的代码在 KMP 侧无法构造对象，在 Pydantic 侧因 `extra="forbid"` 返回 422。这是协议第 1 节“字段不存在比存在但被校验更可靠”的工程实现。

## 13. 浏览器嗅探的双路径设计（v0.2 新增，细化 FR-BR）

原 FR-BR-01 只写了“隔离上下文嗅探”，未区分 Android 端与引擎端的能力边界。v0.2 明确两条路径：

### 13.1 路径 A：引擎端 Playwright 嗅探（主力，P0）

适用于用户提交 URL 后由本地引擎完成全流程。Playwright 的 `new_context()` 提供独立 Cookie jar、存储、缓存；`context.close()` 后痕迹清除。引擎侧监听 `page.on("request")`，按 `resourceType` 和 URL 后缀筛选媒体流。这是协议第 6.2 节 `POST /tasks` 的默认路径，**与 Android WebView 无关**。

### 13.2 路径 B：Android WebView 轻量嗅探（P1，降级/补充）

当用户已经在 Android App 内浏览网页、希望“就地嗅探”而不跳转引擎时，使用 WebView 的 `shouldInterceptRequest` 作为**发现层**。

**机制**：重写 `WebViewClient.shouldInterceptRequest(view, request)`，检查 `request.url` 是否匹配媒体流特征（`.m3u8`、`.mpd`、`.mp4`、MIME 类型 `application/vnd.apple.mpegurl` 等），将发现的 URL 存入隔离列表，**不修改响应体、不注入 JS**。

**已知局限（必须在 PRD 中写明）**：

- `shouldInterceptRequest` 对 **XHR/fetch 发起的请求可能不可靠**，有开发者报告无法拦截通过 `XmlHttpRequest` 加载的流。
- 部分播放器使用 blob URL 或 MSE（Media Source Extensions），媒体地址不直接出现在网络请求中，WebView 层无法发现。
- 嵌入页面的源码混淆（如 JW Player 的编码脚本）使静态解析失效，必须依赖运行时网络监听。

**因此路径 B 的定位是**：**在设备内把直链型媒体流拿到手并交付可播产物**。发现（`shouldInterceptRequest` + JS Hook 两条路汇进同一个嗅探控制器）之后，
本机执行者自己完成下载与封装，**不需要引擎在场**：

- 直链单文件：OkHttp + `.part` 续传，直接落进输出沙箱。
- HLS：`HlsPlaylistParser` 解析清单，`HlsDownloader` 4 并发槽位按序拼出 `.ts`；随后 `TsRemuxer` 用平台媒体 API
  做纯拷贝转封装成 `.mp4`（不引入 FFmpeg），AAC 按访问单元拆开重封以满足 `mp4a` 合规。
  转封装前置音频完整性门禁链（探测阶段两道 + 复检六道 + 拆分音频时的样本对账第七道），任一不过就**保留 `.ts` 并如实降级说明**——判据是「绝不产出哑巴 MP4」。
  实现细节与逐轮取证见 `android/README.md` 与 `docs/reports/smoke-report.md` §27–§29，需求条目见 §6.9。
- 提交引擎仍然是可选项：用户显式切到「引擎」执行者时才走 `POST /tasks`，两端的失败归因各用各的码，
  本地失败不借用协议错误码。

对于 blob/MSE/混淆场景，UI 明确提示「未能发现可下载流，建议尝试引擎嗅探」，**不静默失败，不尝试绕过**；
MSE 页面在截获到底层 HLS 清单时才给出强行下载入口，绝不伪造 `SniffResult`。

**安全约束**：

- WebView 使用**独立的数据目录**（`WebView.setDataDirectorySuffix("bgv_sniff")`），与 App 主 WebView 隔离；任务结束后 `WebView.clearCache(true)` + `clearHistory()` + 清除 Cookie。
- `shouldInterceptRequest` 中发现的结果仅作为 `SniffResult` 候选，`headersHint` 过滤 `Cookie`/`Authorization`，与协议第 3.2 节一致。
- WebView 不启用 `setAllowFileAccess`、不启用 `setAllowUniversalAccessFromFileURLs`。

## 14. 安全与隐私设计的合规映射（v0.2 新增）

v0.1 的 FR-SEC 系列已经从工程角度定义了 SSRF 防护、惰性 Cookie、输出沙箱、日志脱敏。v0.2 将其映射到 **GDPR 数据最小化（Art. 5(1)(c)）** 和 **隐私-by-design** 的合规叙事，便于你在 README 和用户文档中说明“为什么这个架构是合规友好的”。

| FR-SEC 条目           | 工程实现                            | GDPR / 合规对应                                         |
| ------------------- | ------------------------------- | --------------------------------------------------- |
| FR-SEC-01 SSRF 默认拒绝 | 出站校验器，回环/私有/元数据端点全拒，重定向后二次校验    | 安全-by-design，降低数据被诱导外流的风险                           |
| FR-SEC-02 惰性 Cookie | 默认不发送；仅被拒时对默认浏览器、单次请求重试；只读副本不写回 | **数据最小化**：凭据接触面压到“必要时、必要时长、必要时范围”                   |
| FR-SEC-03 输出沙箱      | `0700` 目录、路径白名单、扩展名白名单          | 完整性/保密性（Art. 5(1)(f)），防止落盘到非受控位置                    |
| FR-SEC-04 日志脱敏      | 不打印 Cookie 值/token/完整敏感查询串      | 降低日志成为二次泄露源的风险                                      |
| FR-SEC-07 临时文件清理    | 隔离上下文销毁、缓存 TTL、任务结束清理           | **存储限制**与**删除权（Art. 17）** 的工程前置条件                   |
| 本地转录（FR-DL-06）      | Whisper 本地运行，音频不出设备             | **本地处理即数据最小化在基础设施层的实现**：数据不离开设备，不存在“传输给第三方处理器”的合规负担 |

**需要明确的不适用边界**：本产品**不**处理 GDPR 意义上的“数据主体权利请求”（因为不收集个人数据）；不设账号、不设云端、不产生遥测。如果未来加入任何远程功能（如云转码），必须重新评估 DPIA（Art. 35）和处理器协议（Art. 28）。v0.2 的架构决策是 **“让合规问题尽可能不存在”**，而不是“先收集再合规”。

## 17. v0.2 验收增量（追加到第 9 节）

在原验收标准 1–8 之外，追加：

9. **KMP 模型一致性**：`scripts/check_schema.py` 比较 Kotlin `@Serializable` 导出的 Schema 与 Pydantic `model_json_schema()`，`required` 集合和 `enum` 取值必须完全一致，提交前跑。
10. **WebView 隔离**：连续两次使用路径 B 嗅探，第二次 WebView 不携带第一次的 Cookie；`clearCache`/`clearHistory` 后存储目录无残留。
11. **WebView 诚实降级**：对 blob/MSE 播放页面，路径 B 返回“未发现可下载流”并提示引擎嗅探，不产生虚假的 `SniffResult`。
12. **协议安全约束的编译期固化**：Kotlin 侧无法构造包含 `cookieFile` 的 `Task`；Python 侧 `extra="forbid"` 对未知字段返回 422。

## 18. v0.3 验收增量（本机执行者，M8/M9 已按此复跑）

标准 13–16 的判据全部是「可 grep / 可 ffprobe」的，不接受「看起来正常」：

13. **音频样本对账**：转封装成功时产物音频样本数 == 源 AU 数 == 写入器实际拆出的 AU 数（`auCountGate`）；审计行 `hls_remux_done` / `hls_remux_skipped` 里源与产物两组读数（Samples/Bytes/Frames/RateHz/ContentMs/SpanMs/MaxGapMs）同轮出现，缺一侧就无法归因。
14. **`mp4a` 合规**：`ffprobe -show_packets` 里音频包 `duration` 均匀为 1024 tick（并帧历史形态是 2048…16384），且无样本以 ADTS 同步字 `FF Fx` 开头。
15. **降级不误删**：任一门禁判不合格时 `.ts` 必须仍在原地，完成卡点名原因。判据是一条否命——不存在「`.ts` 被删 + `.mp4` 打不开或哑巴」的组合；只有 `.mp4` 落地成功才允许删源。
16. **本地不借用协议码**：本机路径的失败事件 `code = null`、归因走 `LocalFailures`，引擎错误码不出现在本机判定里。
17. **零第三方 native**：APK 不含 FFmpeg / ffmpeg-kit / yt-dlp 可执行文件；体积变化只应来自本项目代码，产物字节数与预算对照随每轮里程碑验收报告登记。
18. **边界沿用**：DRM（SAMPLE-AES / Widevine / FairPlay）检出即拒绝且不提供下载入口；blob/MSE 不伪造 `SniffResult`（即标准 6、11 在 HLS 清单 `keyformat` 判定上复跑）。
